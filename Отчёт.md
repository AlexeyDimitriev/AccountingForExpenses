# Отчёт по приложению

## Доменная область

Приложение помогает вести личный бюджет: записывать покупки, распределять их по категориям и получать сумму расходов за период. Например, можно выбрать категорию "Доставка еды" за месяц и решить, стоит ли сократить такие траты.

Пользователь получает доступ к приложению через веб-страницу. Он создаёт категории, добавляет расходы, исправляет записи и удаляет их. Список можно отфильтровать по категории и датам. Итоговая сумма рассчитывается по той же выборке, которая возвращается в списке. Нет авторизации, предполагается работа локально, поэтому БД хранит данные одного пользователя.

## Стек и устройство приложения

Бэкенд написан на **Go**: в `go.mod` указана версия 1.26.0, контейнер собирается с Go 1.26.8. HTTP-сервер и маршрутизация используют пакет `net/http`. Клиент обращается к REST API по HTTP/1.1 и передаёт данные в JSON. Для подключения к **PostgreSQL** используется `pgx/v5`, SQL-запросы написаны вручную. В Compose закреплена PostgreSQL 16.15.

Фронтенд состоит из **HTML, CSS и JavaScript** без фреймворков и npm-зависимостей. Он использует `fetch` для обращения к API. Файлы страницы встроены в сервер через `go:embed`, поэтому для запуска не нужен отдельный сервер статики. Docker Compose поднимает базу, миграции и приложение. В контейнере приложения работают скомпилированные бинарные файлы; компилятор Go в нём отсутствует.

Бэкенд разделён по правилам чистой архитектуры (как мы делали в прошлом году):

- `internal/domain` содержит сущности и проверку их данных. Этот слой не зависит от базы или HTTP.
- `internal/application` содержит сценарии CRUD, фильтрацию и подсчёт суммы. Доступ к данным описан интерфейсами репозиториев.
- `internal/infrastructure` реализует работу с PostgreSQL, обработку HTTP и чтение конфигурации.
- `cmd/server` соединяет реализации и запускает сервер; `cmd/migrate` запускает миграции отдельно.

Например, при добавлении расхода HTTP-обработчик разбирает JSON, сервис проверяет данные и существование категории, а репозиторий выполняет параметризованный `INSERT`. Ошибка возвращается через те же слои и преобразуется в HTTP-ответ.

## Основные сущности

| Сущность | Поля | Правила |
| --- | --- | --- |
| Категория (`Category`) | ID, название | Название не должно быть пустым после удаления пробелов по краям |
| Расход (`Expense`) | ID, ID категории, сумма в копейках, дата, комментарий | Сумма положительная, дата корректная, категория существует; комментарий необязателен |

Одной категории соответствует много расходов. Связь закреплена внешним ключом в PostgreSQL. Категорию с расходами удалить нельзя: API вернёт `409 Conflict`. Это ограничение проверяется приложением и самой базой.

Сумма хранится целым числом копеек (`int64` в Go и `BIGINT` в PostgreSQL), чтобы расчёты не зависели от ошибок округления чисел с плавающей точкой. Дата хранится как `DATE`: это день покупки, а не момент времени. При переполнении итоговой суммы сервер возвращает ошибку. Интерфейс также проверяет, что число копеек можно передать в JSON без потери точности JavaScript.

Для обеих сущностей реализованы все операции CRUD: `POST` создаёт запись, `GET` читает список или запись по ID, `PUT` изменяет, `DELETE` удаляет. Маршруты начинаются с `/api/categories` и `/api/expenses`. Эти же операции доступны в интерфейсе. Таблица `schema_migrations` служит для учёта миграций и не является пользовательской сущностью.

## Соответствие 12 факторам

Разбор основан на [методологии Twelve-Factor App](https://12factor.net/ru/). Ниже описаны решения, которые есть в исходниках, и ограничения текущего учебного окружения.

### 1. Кодовая база

Сервер, фронтенд, миграции и конфигурация сборки находятся в одном Git-репозитории.

### 2. Зависимости

Модули Go и их версии объявлены в [go.mod](go.mod), контрольные суммы — в [go.sum](go.sum). При сборке образа выполняются `go mod download` и `go mod verify`. Базовые образы Go, Alpine и PostgreSQL закреплены по digest в [Dockerfile](Dockerfile) и [compose.yaml](compose.yaml).

Фронтенд не загружает библиотеки с CDN. Всё необходимое для работы сервера находится в образе, включая сертификаты и встроенные ресурсы. Инструменты для разработки и тестов перечислены в README: Go, Node.js, Python и C-компилятор для детектора гонок. Для обычного запуска они на хосте не нужны.

### 3. Конфигурация

Адрес подключения к базе, уровень логирования и таймауты читаются из переменных окружения в [config.go](internal/infrastructure/config/config.go). В исходниках нет рабочих паролей и адресов конкретного развёртывания.

Для локального Compose настройки можно хранить в `.env`, который исключён из Git и архива. В `.env.example` оставлены образцы значений. Сам сервер не читает этот файл: Compose передаёт настройки в окружение процесса. Изменение конфигурации не требует пересборки бинарного файла.

### 4. Сторонние службы

PostgreSQL подключается как внешний ресурс через `DATABASE_URL` и параметры `PGUSER`, `PGPASSWORD`, `PGDATABASE`. Адрес базы не зашит в репозиториях. Можно указать другой экземпляр PostgreSQL с нужной схемой, не меняя код сервера.

В учебном окружении база работает в отдельном контейнере, её файлы находятся в именованном томе. Замена или пересоздание контейнера приложения не затрагивает данные. Перед подключением к новой пустой базе нужно применить миграции.

### 5. Сборка, релиз и выполнение

Сборка описана в Dockerfile: сначала загружаются зависимости и компилируются `server` и `migrate`, затем готовые файлы копируются в небольшой образ выполнения. При запуске контейнера исходники не компилируются.

Образ получает тег `accounting-for-expenses:${APP_VERSION}`. Релиз задаётся выбранным образом и конфигурацией окружения. Миграции выполняются перед запуском сервера. Для различимых релизов следует задавать уникальный `APP_VERSION` каждой сборке и сохранять соответствующие настройки. Например, `APP_VERSION=hw1-v1` можно указать в `.env` перед сборкой.

В локальном примере используется изменяемый тег `local`, поэтому сам по себе он не обеспечивает историю релизов. Автоматического выпуска, реестра релизов и отката в проекте пока нет. Разделение сборки и выполнения реализовано, а хранение версий релиза остаётся задачей окружения развёртывания.

### 6. Процессы

Сервер не хранит расходы, категории или пользовательские сессии в памяти процесса либо в локальных файлах. Постоянные данные находятся в PostgreSQL. Пул соединений и данные текущего запроса живут только во время работы процесса и не нужны для восстановления записей после перезапуска.

Любой экземпляр сервера может обработать следующий запрос. Это проверяется сквозными тестами: запись создаётся через один экземпляр, а читается и изменяется через другой.

### 7. Привязка портов

Приложение само открывает HTTP-порт с помощью `net/http`. Отдельный Apache, Nginx или сервер приложений для его запуска не нужен. API, страница и проверки состояния доступны через один порт.

При самостоятельном запуске адрес задаёт `HTTP_ADDR`. В Compose сервер слушает `:8080`, а адрес и порт на хосте задаются `APP_BIND_ADDRESS` и `APP_PORT`.

### 8. Параллелизм

Можно запустить несколько процессов сервера с общей PostgreSQL. У них нет локального состояния, которое потребовало бы закреплять пользователя за одним экземпляром.

В `tests/e2e.py` Compose как раз поднимает две копии `app` и проверяет в том числе одновременное создание расходов. Балансировщик в текущую версию не входит (по заданию будет позже): тесты обращаются к экземплярам по разным портам. Для единой точки входа при масштабировании его предстоит добавить в следующих работах. Масштабирование самой PostgreSQL здесь не реализовано.

### 9. Быстрый запуск и корректная остановка

При старте сервер читает настройки, подключается к базе и начинает принимать запросы. Сборка и миграции вынесены из процесса сервера. Он обрабатывает `SIGINT` и `SIGTERM`: прекращает принимать новые соединения и даёт активным запросам завершиться в пределах `HTTP_SHUTDOWN_TIMEOUT`.

По умолчанию на завершение запросов отведено 10 секунд, а Compose ждёт контейнер 15 секунд. Если запросы не успевают закончиться, сервер отменяет их контекст и закрывает соединения. После остановки закрывается пул PostgreSQL. Проверки `/healthz` и `/readyz` позволяют отличить доступность процесса от доступности базы; `/readyz` не проверяет актуальность схемы.

### 10. Сходство окружений

Для разработки и проверки запуска используется один Compose-файл с PostgreSQL фиксированной версии. Приложение не переключается на SQLite или файловое хранилище в локальном режиме. Тот же образ сервера можно запустить в другом окружении, передав другую конфигурацию.

В модульных тестах репозитории заменяются тестовыми реализациями, но SQL и ограничения базы проверяются отдельно на настоящей PostgreSQL. Сквозные тесты собирают и запускают обычный образ приложения. Отдельного production-окружения сейчас нет, поэтому фактическое совпадение с ним не проверялось; проект предоставляет общую конфигурацию для воспроизводимого запуска.

### 11. Журналирование

Сервер пишет структурированные JSON-события через `log/slog` в стандартный вывод. Для HTTP-запросов фиксируются метод, путь, статус, размер ответа и длительность. Приложение не создаёт локальные файлы журналов и не занимается их ротацией.

Команда миграций использует стандартный вывод ошибок `slog`. Оба потока собирает среда запуска: в Compose их можно посмотреть через `make docker-logs`. Отдельное хранилище и обработчик логов в учебное окружение не включены.

### 12. Задачи администрирования

Миграции запускаются отдельной командой `cmd/migrate`. В Compose это разовый контейнер из того же образа, что и сервер, с теми же настройками подключения к базе. Повторно запустить команду можно через `make docker-migrate`.

Миграции встроены в бинарный файл и версионируются вместе с приложением. Применение выполняется в транзакции, блокировка PostgreSQL исключает одновременное выполнение несколькими процессами. Таблица `schema_migrations` хранит имена и контрольные суммы применённых файлов. Повторный запуск безопасно пропускает неизменённые миграции, а изменение уже применённого файла приводит к ошибке.
